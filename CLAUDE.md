# MicroFoundry Development Workflow

This project uses **5 Claude development agents** that work sequentially on Epics.
Each agent has a specific role and communicates through GitHub Issues and Pull Requests.

## Project Context

MicroFoundry is a micro CloudFoundry for Kubernetes. The platform provides:
- Application runtime on K8s (Docker Desktop, EKS, GKE, AKS)
- Backing service binding (AWS RDS, BigQuery, etc.) via Open Service Broker API
- Network services (Kong, Nginx, AWS API Gateway)
- Built with **Go** (API, orchestration, CLI) and **Rust** (performance-critical runtime)

Reference repos for architecture patterns:
- `../cli/` — CloudFoundry CLI (Go) — command/actor/API patterns, resource types
- `../cf-deployment/` — CF deployment manifest — component topology, 17 instance groups
- Architecture doc: `docs/cloudfoundry-architecture.md`

## Agent Workflow

When the user provides an **Epic** (feature request), execute the following agents **in order**.
Each agent writes its output to the GitHub Issue or PR so there is a permanent record.

```
User Epic Request
    │
    ▼
┌─────────────────────┐
│ 1. Analyzer Agent    │──→ Creates GitHub Issue with detailed plan
│                      │──→ Creates epic/* branch
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 2. Data Engineer     │──→ Posts data structure comment on Issue
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 3. Product Designer  │──→ Posts UI assessment/mockup comment on Issue
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 4. Developer Agent   │──→ Writes code on epic/* branch
│                      │──→ Builds and tests
│                      │──→ Creates Pull Request
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 5. Review Agent      │──→ Posts review on PR (license, security, perf, cost)
│                      │──→ Waits for human merge
└─────────────────────┘
```

## Agent 1: Analyzer Agent

**Trigger**: User gives an Epic title and description.

**Process**:
1. Read the Epic description carefully
2. Read `docs/cloudfoundry-architecture.md` for CF architecture context
3. Scan relevant reference code in `../cli/` and `../cf-deployment/` based on the Epic topic
4. Use deep thinking (ultrathink) to design a comprehensive implementation plan
5. Create a GitHub Issue on `younjinjeong/microfoundry` with the plan
6. Create a branch `epic/<slugified-title>` from `main`

**GitHub Issue format**:
```markdown
# Epic: <title>

## Original Request
<user's description>

---

## Implementation Plan

### Background & Motivation
<why this matters for MicroFoundry>

### CF Component Mapping
<which CF components are relevant, MicroFoundry K8s equivalent>

### Task Breakdown
1. <task with acceptance criteria>
2. <task with acceptance criteria>
...

### API Contracts
<REST/gRPC endpoints with request/response shapes>

### Architecture Decisions
<key design choices and trade-offs>

### Testing Strategy
<unit, integration, smoke tests>

### Deployment
<K8s resources, Docker images, configuration>

---
*Generated by Analyzer Agent*
```

**Labels**: `epic`, `agent-generated`

**Commands** (use `gh` CLI):
```bash
gh issue create --repo younjinjeong/microfoundry --title "[Epic] <title>" --body "<body>" --label epic,agent-generated
git checkout -b epic/<slug> main
git push -u origin epic/<slug>
```

## Agent 2: Data Engineer Agent

**Trigger**: Analyzer Agent has created the Issue.

**Process**:
1. Read the GitHub Issue (title + body) created by Analyzer
2. Analyze what data structures, schemas, and API types are needed
3. Design Go structs (with JSON/YAML tags), database schemas, protobuf definitions
4. Post recommendations as a comment on the Issue

**Comment format**:
```markdown
## Data Engineering Review

### Go Structs
<code blocks with struct definitions>

### Database Schema
<SQL CREATE TABLE statements if applicable>

### API Request/Response Types
<code blocks with types>

### Serialization Format
<JSON/YAML/Protobuf recommendation with rationale>

### Relationships & Indexes
<entity relationships, recommended indexes>

---
*Generated by Data Engineer Agent*
```

**Command**:
```bash
gh issue comment <number> --repo younjinjeong/microfoundry --body "<comment>"
```

## Agent 3: Product Designer Agent

**Trigger**: Data Engineer Agent has posted its comment.

**Process**:
1. Read the GitHub Issue and all comments
2. Assess: does this Epic need a web-based user interface?
3. If NO UI needed → post a brief comment saying CLI-only, proceed
4. If UI needed → generate a self-contained HTML mockup (inline CSS/JS) and post as a comment

**Comment format (no UI)**:
```markdown
## Product Design Assessment

No web interface required for this Epic. Feature will be CLI/API only.

---
*Generated by Product Designer Agent*
```

**Comment format (with UI)**:

<why UI is needed, what pages/components>

<details>
<summary>Click to view HTML source</summary>

\```html
<!DOCTYPE html>
...complete self-contained HTML...
\```

</details>

---
*Generated by Product Designer Agent*
```

## Agent 4: Developer Agent

**Trigger**: All previous agents have posted their comments on the Issue.

**Process**:
1. Read the Issue and ALL agent comments (plan, data structures, design)
2. Checkout the `epic/<slug>` branch
3. Write code following the plan:
   - Use Go for API/orchestration/CLI code
   - Use Rust for performance-critical components
   - Follow existing project patterns and conventions
   - Include unit tests alongside implementation
4. Build and verify:
   - `go build ./...` must pass
   - `go test ./...` must pass
   - If Dockerfile exists, `docker build` must succeed
5. Commit with meaningful messages referencing the Issue
6. Push the branch and create a Pull Request

**PR format**:
```markdown
## Summary
<1-3 sentences describing what was implemented>

Resolves #<issue-number>

## Changes
- <file: what changed>
- <file: what changed>

## Test Plan
- [ ] `go build ./...` passes
- [ ] `go test ./...` passes
- [ ] Docker image builds
- [ ] Manual verification of <specific feature>

---
*Generated by Developer Agent*
```

**Commands**:
```bash
git add <specific files>
git commit -m "feat: <description>\n\nRefs #<issue>"
git push origin epic/<slug>
gh pr create --repo younjinjeong/microfoundry --title "feat: <title>" --body "<body>" --base main --head epic/<slug>
```

**Code standards**:
- Go: `gofmt` formatted, pass `golangci-lint`
- Rust: `cargo fmt`, pass `clippy`
- No hardcoded secrets
- Structured logging with `log/slog`
- Error handling: no silent failures, wrap errors with context

## Agent 5: Review Agent

**Trigger**: Developer Agent has created the PR.

**Process**:
1. Read the PR diff (`gh pr diff <number>`)
2. Perform 5 review checks:

   **a. License Compliance**
   - Scan all dependencies for copyleft licenses (GPL, AGPL, LGPL)
   - Flag any that conflict with project license
   - Run `go list -m all` to enumerate deps

   **b. Security**
   - Check for hardcoded secrets, SQL injection, command injection
   - Look for OWASP Top 10 vulnerabilities
   - Run `govulncheck ./...` if available
   - Review any external input handling

   **c. Performance**
   - Identify potential bottlenecks (N+1 queries, unbounded allocations)
   - Check goroutine/thread safety
   - Review resource usage patterns

   **d. Cost Effectiveness**
   - Review K8s resource requests/limits in manifests
   - Estimate cloud resource costs if applicable
   - Suggest optimizations

   **e. Right-Sizing**
   - Check buffer sizes, connection pool sizes, replica counts
   - Verify resource requests match expected load

3. Post review as a PR comment with PASS/WARN/FAIL for each area
4. If any FAIL → use `gh pr review --request-changes`
5. If all PASS/WARN → use `gh pr review --comment`

**Review comment format**:
```markdown
## Review Agent Report

### License Compliance: PASS/WARN/FAIL
<details and findings>

### Security: PASS/WARN/FAIL
<details and findings>

### Performance: PASS/WARN/FAIL
<details and findings>

### Cost Effectiveness: PASS/WARN/FAIL
<details and findings>

### Right-Sizing: PASS/WARN/FAIL
<details and findings>

### Summary
<overall assessment, blocking issues if any>

---
*Generated by Review Agent — awaiting human review and merge*
```

## Branch & Merge Strategy

- Each Epic gets its own branch: `epic/<slugified-title>`
- All work happens on the Epic branch
- PR merges use **squash merge** to keep `main` history clean
- Only the human (project owner) approves and merges PRs
- After merge, the Epic branch is deleted
